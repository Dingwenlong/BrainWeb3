# BrainWeb3 应用设计文档

> 版本：v1.0 ·  最后更新：2026-06-17 ·  阶段：P5 模拟验收（已上线公开演示版）

---

## 1. 概述

### 1.1 定位
**BrainWeb3（脑域链医）** 是一个围绕**脑电（EEG）数据**的安全治理平台，把「数据接入 → 链上存证 → DID/VC 授权 → 联邦学习 → 审计追溯 → 可视化分析」收敛到同一套全栈 monorepo 中。核心诉求是：在**敏感医疗级脑数据**的全生命周期里，提供**可治理、可追溯、可验证**的合规闭环。

### 1.2 关键能力
- **数据资产化**：EEG 文件上传 → 链下存储 → 链上存证（SM3/哈希 + IPFS CID + 交易哈希）。
- **访问治理**：按数据集/机构/角色的访问申请—审批—撤销，带时限授权。
- **联邦训练**：在已授权数据集上发起训练任务，产出可治理的模型版本。
- **身份治理**：DID + 可验证凭证（VC）的签发/挂起/吊销，全程留痕。
- **数据销毁**：被遗忘权闭环（申请→审批→执行→存储清理→证据上链）。
- **审计与上链**：所有关键操作写审计事件，并按策略选择性锚定到区块链。

### 1.3 文档范围
本文覆盖系统**总体架构、技术栈、角色权限、功能模块与领域状态机、数据模型、API 概览、安全与身份设计、前端设计、部署架构、已知边界**。不含逐接口字段级契约（见 `docs/接口与错误码规范.md`）与逐功能的详细 TSD。

## 2. 总体架构

### 2.1 部署单元与依赖
系统由 **4 个可部署单元** + **5 类外部依赖**组成：

| 单元 | 技术 | 端口 | 职责 |
|---|---|---|---|
| frontend | Vue 3 + Vite（静态 SPA） | 80/443（经 Caddy） | 神经控制台界面 |
| backend | Spring Boot 3.3.5 / Java 17 | 8080 | 业务编排、鉴权、链/存储网关 |
| eeg-service | Flask + numpy + mne | 8101 | EEG 元数据解析、脑区活跃度计算 |
| federated-service | Flask（占位） | 8102 | 联邦训练编排占位（当前 mock） |

| 依赖 | 用途 | 备注 |
|---|---|---|
| MySQL 8 | 业务持久化（JPA + Flyway 迁移 V1–V14） | 必需 |
| FISCO BCOS 3.x | 业务事件 / 数据资产上链存证 | 可关闭→走 Mock 网关 |
| MinIO / 本地磁盘 | 数据集对象存储 | `STORAGE_PROVIDER` 切换 |
| IPFS | 存证 CID 归档层 | 可选 |
| Redis | 预留（当前代码未消费） | — |

### 2.2 拓扑（单源反向代理）

```
                         ┌──────────────────── 一台主机 / 一组容器 ────────────────────┐
   浏览器 ── HTTPS ──────▶ web (Caddy 80/443)                                           │
                         │   ├─ /            → 静态 SPA                                   │
                         │   └─ /api/*       → reverse_proxy → backend:8080  (同源,无CORS)│
                         │                                                               │
                         │  backend (Spring Boot 8080)                                    │
                         │     ├─ JDBC ───────────────▶ mysql:3306                        │
                         │     ├─ EEG_SERVICE_BASE_URL ▶ eeg-service:8101                 │
                         │     ├─ ChainGateway  ───────▶ FISCO BCOS  /  MockChainGateway  │
                         │     └─ StorageGateway ──────▶ MinIO  /  LocalStorageGateway    │
                         └────────────────────────────────────────────────────────────────┘
```

**设计要点：单源反向代理**——前端与 `/api` 同源（都经 Caddy），后端无需配置 CORS，前端零改动，HTTPS 由 Caddy 自动签发。

### 2.3 可插拔网关（Mock ↔ Real）
后端通过 `GatewayConfiguration` 按环境变量注入网关实现，使系统在「演示/本地」与「正式」之间无缝切换：

| 网关 | 选择条件 | Mock 实现 | Real 实现 |
|---|---|---|---|
| `ChainGateway` | `CHAIN_ENABLED && provider=fisco-bcos-3` | `MockChainGateway`（`mock://`、`SM3:`/`HASH:` 前缀回执） | `FiscoBcosChainGateway`（懒加载 SDK，解析/自动部署合约） |
| `StorageGateway` | `STORAGE_PROVIDER=local\|minio` | `LocalStorageGateway`（`local://…`） | `MinioStorageGateway`（`minio://bucket/…`，可自动建桶） |
| `FederatedTrainingGateway` | 当前仅 Mock | `MockFederatedTrainingGateway`（`mock-fate`，启发式产出 AUC/F1 演示指标） | （未实现，留待接入 FATE 等） |

## 4. 角色与权限模型

### 4.1 角色
四种操作者角色（`ActorProfile.actorRole`，大小写不敏感）：

| 角色 | 含义 | 典型权限 |
|---|---|---|
| `researcher` | 研究员 | 提交访问申请、查看已授权数据/脑活跃度、发起训练 |
| `owner` | 归属方 | 代表机构审批访问/销毁、巡检审计、直接读本机构资产 |
| `approver` | 审批人 | 专注审批流与权限决策 |
| `admin` | 管理员 | 全局监管：账户治理、链记录监管、身份中心、全量审计 |

- **特权判定**：`isPrivilegedActor = role ∈ {owner, approver, admin}`；`isAdmin = role === admin`。

### 4.2 可见性规则（贯穿各服务）
- **admin**：全部数据。
- **owner / approver**：本机构（actorOrg）范围。
- **requester / actor**：仅自己创建/相关的记录。

后端通过 `ActorContextResolver → ActorContext` 解析当前操作者上下文，授权校验下沉到各 Service 层（如 `AccessRequestService.canAccessDataset`）。

## 5. 功能模块与领域流程

### 5.1 模块全景（前端页面 ↔ 后端模块）

| 前端页面 | 后端模块 | 信号色域 | 职责 |
|---|---|---|---|
| 总览 Overview | system-status / datasets | 青（数据） | 工作台首页、上传入口、链路状态 |
| 数据详情 DatasetDetail | datasets / eeg | 青 | 3D 脑热力图、脑区指标、存证/门禁/销毁 |
| 访问申请 AccessRequests | access-requests | 紫（治理） | 申请—审批—撤销 |
| 销毁流程 Destruction | destruction | 红（销毁） | 被遗忘权闭环 |
| 训练任务 TrainingJobs | training-jobs | 青（计算） | 任务发起与进度 |
| 模型治理 ModelRecords | model-records | 紫/青 | 模型版本与治理状态 |
| 身份中心 IdentityCenter | identity | 紫（身份） | DID / VC 状态与历史 |
| 账户管理 Accounts | auth / account | 紫（系统） | 账户、密码、凭证 |
| 审计中心 Audits | audits | 青/琥珀 | 关键操作时间线 |
| 链记录 ChainRecords | chain-records / chain-policy | 青/紫 | 上链状态与策略 |

### 5.2 核心生命周期（端到端）

```
上传 ──▶ 存储 ──▶ 存证(链) ──▶ 访问申请 ──▶ 审批 ──▶ 脑活跃度分析 ──▶ 联邦训练 ──▶ 模型治理 ──▶ 销毁 ──▶ 审计/上链
 │        │         │             │          │          │              │            │          │
received persisted notarized   pending   approved   (EEG svc)       running     candidate  destroyed
                                                                     succeeded   →active    →purged
```

每个阶段都会：① 写**审计事件**（无条件）；② 按**链策略**选择性**锚定上链**。

### 5.3 状态机汇总

**数据集（dataset）的四条状态轴**
- `uploadStatus`：received → uploaded（存储成功）/ failed。
- `proofStatus`：pending-storage → storage-persisted → **notarized**；链失败 → finalization-failed（可重试收口）。
- `trainingReadiness`：review-required → **authorized-ready**（存证后）→ blocked（销毁/上传失败）。
- `destructionStatus`：active → pending-destruction → approved-for-destruction → destroyed。

**访问申请（access_requests）**
`pending → approved`（写 `expiresAt`）/ `rejected`；`approved/pending → revoked`（立即过期）。批准链 `ACCESS_APPROVED`，撤销链 `ACCESS_REVOKED`。

**训练任务（training_jobs）**
`create → running →（refresh）→ succeeded / failed`。成功后 `ModelRecordService` 自动登记模型（`candidate`）。链 `TRAINING_COMPLETED` / `TRAINING_FAILED`。

**模型治理（model_records）**
`candidate ↔ active`、`candidate/active → archived`、`archived ↔ active`。每次变更链 `MODEL_GOVERNED`；治理泳道给出版本对比（排名 x/y、与最新偏移、按算法/状态计数）。

**数据销毁（destruction_requests）**
`pending → approved → executing → completed`（逻辑删除，链 `DESTRUCTION_COMPLETED`）→ `purge-storage`（`cleanup: not-requested → in-progress → completed`，生成 SHA-256 清理证据，链 `DESTRUCTION_STORAGE_PURGED`）；拒绝回退 active。

### 5.4 区块链事件策略（ChainPolicyService）
- **必须上链（required）**：`ACCESS_APPROVED`、`ACCESS_REVOKED`、`TRAINING_COMPLETED`、`TRAINING_FAILED`、`DESTRUCTION_COMPLETED`、`DESTRUCTION_STORAGE_PURGED`、`MODEL_REGISTERED`、`MODEL_GOVERNED`。
- **可选（optional）**：其余事件类型的默认回退。
- **仅审计（audit-only）**：经 `disabledEventTypes` 配置；`shouldAnchor()=false` 时记录 `anchorStatus=policy-skipped`，不调用链网关。

### 5.5 加密与哈希策略
- **上传指纹**：`SHA-256(fileBytes + subjectCode + title)`，用于收口重试。
- **链哈希**：FISCO `cryptoSuite.hash()` → SM3（国密）或 SHA-256，结果前缀 `SM3:` / `HASH:`。
- **销毁证据**：`SHA-256(datasetId|provider|storageKey|actorId|cleanedAt)`。
- **DID**：`did:brainweb3:{机构名 slug}`；**IPFS CID** 与 off-chain 引用（存储 URI / `brainweb3://chain-event/...`）随存证回执返回。

### 6.1 实体关系（核心）

```
app_users ─┐
           ├─< refresh_tokens

datasets (1)─(1) data_asset_proofs
```

| **identity_credential_history** | id BIGINT | previous_status→next_status, source(manual/derived/legacy-config), reason（不可变历史） |
| **destruction_requests** | id VARCHAR(40) | requester_*, `status`, approver_*, executed_by, `cleanup_status`, cleanup_evidence_ref/hash, executed_at, cleanup_completed_at |

## 8. 安全与身份设计

### 8.1 认证
- **JWT Bearer**：`POST /auth/login`（actorId + password）签发 `token` + `refreshToken`，前端存 localStorage（`brainweb3-auth-session`）。
- **会话恢复**：应用加载时 `GET /auth/session` 校验；失败则 `POST /auth/refresh` 轮换；再失败清会话。
- **密码**：修改密码会吊销全部刷新令牌；重置走一次性票据（`/auth/password-reset/{request,confirm}`，带 TTL 与 consumed 标记）。

### 8.2 授权与账户治理
- 角色 + 机构可见性（§4.2）。
- `AccountService` 保证**任意账户变更后仍至少存活一个 active admin**。

### 8.3 身份治理（DID / VC）
- `IdentityCredentialGovernanceService` 维护主体（user/dataset/model）的凭证状态：`issued`（账户 active）、`suspended`（disabled）、`revoked`（manual / legacy-config）。
- 状态变更写入**不可变历史**（`identity_credential_history`），来源标注 manual / derived / legacy-config，并记审计 `*_CREDENTIAL_STATUS_UPDATED`。

### 8.4 运行时安全护栏（RuntimeSecurityGuardrails）
启动期校验，**仅在非生产态豁免**：`stage ∈ {bootstrap, local, dev, test, ci}` 时跳过；其余「生产态」强制要求：
1. 替换默认 JWT 密钥、默认身份凭证密钥、默认演示密码；
2. 关闭演示账号 bootstrap 与演示密码登录。

> ⚠️ 设计含义：**公开演示版**需把 `APP_STAGE=bootstrap`（保留演示登录）；**正式生产**则用真实 `stage` + 强密钥 + 关演示登录。

### 8.5 其它
- `SensitiveTextSanitizer`：对链/状态输出做敏感信息脱敏（`detailsRedacted`）。
- **必须上链事件**（§5.4）提供合规级可验证追溯。

## 9. 前端设计 ——「神经控制台 / Neural Console」

### 9.1 设计系统
- **暗色令牌**：底色 `--bg-page #060a14` / `--bg-page-alt #0a1020`，叠加青/紫径向辉光 + 仪表网格，玻璃面板 `backdrop-filter: blur(14px) saturate(118%)`；文本 `--text-strong #eef5fc` / `--text-main #c4d3e5` / `--text-muted #8696ac` / `--text-faint #8492aa`（AA 底线）。
- **信号色语义**：**青 `#34e1d6`** = 数据/工作台/激活；**紫 `#a07bff`** = 治理/身份/系统域；**琥珀 `#f2b259`** = 警告/待办；**红 `#ff6173`** = 销毁/失败。
- **字体**：`--display` Chakra Petch（标题/品牌）、`--body` Noto Sans SC（正文，CJK 优化）、`--mono` JetBrains Mono（数字/ID/状态/读数）。
- **母题与动效**：登录页循环流动的 **EEG 电流**（青向前、紫反向）、品牌脉冲突触（`signalPulse`）、`consoleRise` 错落入场、**3D 脑热力图**冷→热配色（深蓝→青→品红）。全局 `prefers-reduced-motion` 降级。

### 9.2 路由与守卫
- 11 条认证路由 + `/login`；`meta.requiresAuth` 守卫：未登录访问受保护页 → 重定向 `/login?redirect=…`；已登录访问 `/login` → 跳 `/`；应用挂载时恢复会话。

### 9.3 角色自适应 UI
- 导航分三域（**工作台 / 治理 / 系统**），标签随角色变化（如「模型治理 vs 模型记录」「访问申请 vs 我的申请」「监管审计 vs 审计中心」），链记录入口仅特权可见。
- 视图内动作分级：researcher 在访问申请页为**只读巡检**，特权用户才有审批/撤销按钮；数据详情页的脑区指标与审批流按特权显隐。

### 9.4 关键组件
`PageHero`（页头 + EEG 母题）、`SurfaceCard`（玻璃卡）、`Brain3DHeatmap`（懒加载 Three.js 3D 脑）、`ActivityTimeline`、`RegionMetricsPanel`、`AppToastStack`（success/warning/danger 提示）。

## 10. 部署架构

### 10.1 容器化
- 三个应用镜像（`backend` / `web`(Caddy+SPA) / `eeg-service`）+ `mysql:8.0`，由 `docker-compose.prod.yml`（可叠加低内存调优 `deploy-tune.yml`）编排。
- **CI 预构建**：`.github/workflows/build-images.yml` 在 GitHub Actions 构建并推送镜像到 **GHCR**；低配服务器只 `docker compose pull` 免编译。
- **单源 Caddy**：`deploy/Caddyfile` 服务 SPA + 反代 `/api`，域名模式下自动 HTTPS。

### 10.3 正式环境差异
正式部署需：真实 `stage` + 强密钥、`CHAIN_ENABLED=true` + 部署 FISCO 节点/合约、`STORAGE_PROVIDER=minio` + 对象存储、托管 MySQL、放行/签发 HTTPS（大陆地域域名需 ICP 备案，或迁香港）。详见 `docs/P5 正式环境联调清单.md`。
